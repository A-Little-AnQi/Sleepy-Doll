# 能力发现与执行流程

## 本机工具名对照

本文按通用叫法书写；在 Sleepy Doll 里对应的是下面这些真实工具。**不要调用对照表以外的名字** —— 尤其注意 `capability.*` 指的是宿主的动态能力目录，落到工具上是 `bgi.api.*`；`bgi.capability.*` 是插件声明的语义能力层，未装插件时恒为空。

| 本文叫法 | 实际工具 | 用途 |
| --- | --- | --- |
| `state.get` | `bgi.state.get` | 读取宿主当前状态、截图器与窗口情况 |
| `capability.search` | `bgi.api.search` | 在宿主接口目录里按业务词发现设置与动作 |
| `capability.describe` | `bgi.api.describe` | 读取某个 `methodId` 的用途、参数、前置、副作用与回退边界 |
| 只读调用 | `bgi.api.read` | 调用已确认的只读接口 |
| `capability.invoke` | `bgi.api.invoke` | 调用已确认的写接口，运行时跟踪到终态 |
| `task.status` | `bgi.job.get` | 查询已有 Job；接纳响应里已经带终态时不要重复查询 |
| `task.cancel` | `bgi.job.cancel` | 取消 Job |
| 用户资源 | `bgi.user.list` / `bgi.user.read` / `bgi.user.inspect_script` / `bgi.user.write` / `bgi.user.restore` | 读写 `User\` 下的文件；具体顺序见 `bgi-operator` 技能 |
| 插件语义能力 | `bgi.capability.search` / `bgi.capability.describe` / `bgi.capability.invoke` | 仅在任务明确涉及已安装插件时使用 |

同样的对应关系也适用于其他文档：凡是提到“能力目录”，在 Sleepy Doll 里就是 `bgi.api.*`。

## 何时主动用工具

下列问题不能只靠聊天回答：当前是否就绪、当前设置是什么、某脚本是否已订阅、当前版本是否暴露某能力、正在跑什么、帮用户开始/停止/修改、以及“我这里为什么不行”。这些场景由 Agent 主动查询，用户不需要说“调用接口”。

纯概念说明或与现场无关的教程可以直接回答。若用户问“能不能做到”，而答案取决于当前能力目录，也要搜索后再答。

调用前先按 [capability-boundaries.md](capability-boundaries.md) 判断。无关问题、不可知的私人事实，以及已经明确不存在的完整功能不进入能力搜索。用户要求现场制作新脚本时，只有感知、数据、动作与验证能够闭环，才继续发现和组合原子能力。

## 标准循环

1. 将用户原话归一化成“动作 + 对象 + 约束”，并补入 [bgi-domain.md](bgi-domain.md) 中的 BetterGI 术语。
2. 只有当游戏状态会影响下一步时才调用 `bgi.state.get`，例如要执行游戏任务、排查识别、查看活动任务。不要把它机械地加到每次闲聊前。
3. 用目标语义调用 `bgi.api.search`。搜索内容应同时包含用户词与 BGI 规范词，例如“刷两次无相之水 不领取奖励 自动首领讨伐”。不要只搜索猜测的 C# 方法名。
4. 首次结果不可靠时，换同义词或上位类别再搜。通常最多三轮；至少完成一次用户词归一化和一次类别扩展后，才能判断当前没有合适能力。
5. 对最可能的少量候选调用 `bgi.api.describe`，确认参数、前置条件、副作用、异步方式和返回证据。不要描述几十个候选，也不要把 schema 展示给用户。
6. 缺少必要参数时，只询问用户能理解且会改变结果的条件，例如刷哪个首领、几次、是否花树脂、用哪支队伍。默认值可靠时直接采用，并在结果中自然说明。
7. 对需要更新仓库、订阅、配置再运行的请求，先形成内部执行计划并逐步调用所需能力。用户对最终目标的明确授权同时覆盖完成它所必需的常规准备动作，不必逐项请求批准。
8. 调用 `bgi.api.invoke`。长任务保留 task id，在需要时通过 `bgi.job.get` 查询；不要把 task id 当作面向用户的名称。
9. 用返回的结构化证据判断成功、进行中、失败或部分完成。不要根据“调用没报错”就声称游戏内目标已完成。

## 搜索与选择约束

- 搜索的是用户目标，不是技术结构。页面导航和明确 UI 命令可以来自 ViewModel，但应以用户可见页面/功能名建立索引；`Service`、`Manager`、程序集名和命名空间只可作为开发排障线索。
- 优先高层领域能力。不要因为 `keyPress`、`click` 或文件写入更容易搜索到，就用它们重新实现已有任务。
- 对“收集/刷取某物”这类复合目标，不要在找到“打开脚本仓库”后停止搜索；继续寻找仓库更新、内容读取、订阅、设置和运行能力，直至能够闭环完成。
- 不猜 capability id、枚举值、路径、队伍名、脚本名或配置键。所有标识来自搜索、状态或描述结果。
- 若能力未暴露，明确说“当前版本里没有找到能直接完成这件事的能力”，并指出缺口；不要说 BetterGI 本身一定不支持。已在能力边界中确定不存在的完整功能除外，此类请求无需搜索，直接准确说明没有。
- 若一个请求分成多个步骤，逐步验证关键状态；某一步失败后不要继续执行依赖它的后续步骤。

## 错误翻译

| 内部结果 | 对用户的说法 |
| --- | --- |
| `GAME_NOT_READY` | “原神或 BetterGI 还没进入可操作状态。”随后说清应打开什么或等待什么。 |
| `BUSY` / 任务冲突 | “BetterGI 正在运行「用户可见任务名」；需要先等它结束或停止它。” |
| `CAPABILITY_NOT_FOUND` | “当前版本里没找到能直接完成这件事的能力。”说明已经查过的功能类别和实际缺口。 |
| 参数校验失败 | 直接询问缺少的业务参数，不说 schema、类型或反序列化。 |
| 前置条件不满足 | 说明具体前提，例如队伍不存在、脚本未订阅、分辨率或小地图设置不符合要求。 |
| 超时或识别失败 | 说明停在哪个可见阶段、已确认的证据和下一项最可能的检查。 |
| 内部异常 | 先给普通用户结论；只有开发者模式才附能力 id、异常类型和原始错误摘要。 |

## 用户可见回复

工具调用前通常不播报“我先查询接口”。需要等待长任务时，只说“我先看看 BetterGI 当前是否能开始”或直接给进展。调用后优先使用以下形态：

- 已完成：“自动拾取已经打开。”
- 已开始：“已经开始刷无相之水，计划 2 次，不领取奖励。”
- 需要选择：“可以跑。你想刷经验花还是摩拉花？这会影响路线和奖励设置。”
- 被阻塞：“现在正在跑「每日委托」，所以地图追踪暂时不能启动。要先停掉它吗？”

不要输出“已成功调用 `FooService.BarAsync`”“宿主返回 200”或“通过反射设置属性”。
